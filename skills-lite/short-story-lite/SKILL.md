# 小说写作流程（精简档）

本模式只装一位审读员。流程与派发规则全在这一份文件里，**没有额外的派发面板要读**；文风契约是另一份技能（有它自己的写法示例，按需查阅）。需要五位角色化读者时，另开会话选「短篇小说模式」。

写正文或改稿前加载 `writing-style-contract`；它的写法示例按需查阅（skill 工具只加载当前 SKILL.md，不自动加载参考文件）。参考路径以 skill 工具返回的技能目录为基准，不在其他作品目录里搜索。**契约正文里提到 `short-story` 技能、共用流程或审读面板的段落都指完整版**，本模式不读那份技能，也不按五角色分工派发。

## 1. 请求对应的最小流程

| 请求 | 必须完成的工作 |
|---|---|
| 新写或续写整篇、片段、单场景、开头、对话 | 定范围与停止点 → 按规模规划 → 成稿 → **派一位合并审读员** → 按报告修订、必要时复核 → 交付 |
| 整体改稿或实质性改写 | 读取现稿与相关设定 → 按确认范围修改 → 派一位合并审读员审新版 |
| 局部措辞、标点或一句一段的润色 | 读取必要上下文 → 修改 → 主代理核对改动与接缝；若改变事实、动机、因果、视角或动作状态，再派那位审读员 |
| 只要评价 | 阅读获准材料 → 派合并审读员 → 汇总意见；不修改正文，不擅造作者设定 |
| 只要方案或大纲 | 明确范围 → 按规模准备人物与节拍；涉及关系转折时核对依据 → 主代理自查 → 交付方案，不自动写正文 |

片段不需要全篇闭环，不为验收补写范围外的故事。方案阶段不派读者。

## 2. 先让作者确定方向与篇幅

新写或续写前核对交付形态、内容重点、停止位置，以及作者已明确的字数、人物、视角。只有关键选择缺失且无法从上下文判断时，才用 `ask_user_question` **一次问完**；"写一段""短一点"可以自行选合理篇幅并简短说明。

单点近似目标如"约 2000 字"默认允许约 ±15% 浮动；作者给区间时优先落在区间内。明确的精确字数、最低或最高字数按硬约束执行。小幅偏差不自动触发补写、删字或新一轮审读。已给出的要求不重复问。

篇幅档位仅供参考：微型 3k–5k、标准短篇 5k–10k、中短篇 10k–20k、系列每篇 3k–10k。

## 3. 规划与文件边界

较长新项目可用 `brief.md` 存方向、`bible.md` 存人物卡、`outline.md` 存节拍、`draft.md` 存正文；短片段可以在当前任务里保留简短规划，**不强制建四个文件**。人物卡写身份、当下动机或需要、关系、性格与口吻、当前状态与相关事实；节拍写先后、快慢详略、字数与停止点。已有项目沿用原路径，只补受影响内容。

**这是写作工作区，不是你的个人项目。** 只读、只改写作者让你改的文件；不新建作者没要的文件，不重命名、移动或删除既有文件。新增必要文件前先说明用途。

禁止为避免重名或了解背景对其他故事目录做全局 `glob`、`grep` 或目录枚举；新目录只检查拟用路径是否存在。搜索、读取和审读派发都不能超出作者授权。

## 4. 四个只读工具

它们是**主代理的自查与定位手段**，都不进审读流程，也不能替代审读：

- `story_wordcount`：实测字数、记录正文版本、查看场景分布。汇报给作者的数字必须来自它；偏离提示只是数据，不是质量判定或自动改稿命令。
- `story_bible`：人物卡字段核对、术语表读取、与正文的提及次数交叉检查。
- `story_lint`：字面线索清单。命中不构成违规，未命中不表示合格；视角、时态、情绪是否解释过度、节奏与必要交代都要由审读员结合正文判断。
- `story_doctor`：安装自检。模式挂不上、技能读不到、patch 被覆写时用它定位。

## 5. 独立审读（本模式的核心差异）

**新稿、续写新增正文、整体改稿和改变故事事实的实质性修改必须派一次审读。** 纯措辞、标点及不改变事实与阅读含义的局部润色由主代理回读改动与接缝即可，并在交付时说明这是自查。

派发规则：

1. **只有一位审读员**：工具 `subagent_review`。角色说明、五维判据、报告格式与只读限制都装在它身上，派发时**只给变量**：正文绝对路径、稿件版本、范围与停止点、作者的有效要求、以及本次要它看的材料清单。不要复述人设；把角色与版本写进 `description`，之后好认人。
2. **冷读优先**：默认只让它读正文，不提供人物卡、节拍、大纲或你的写作推理——读者的价值就是不知道你想干什么。确实需要它对照设定时，把该文件列进派发消息并说明用途。
3. **一次读全文，一份报告覆盖五个维度**：读不懂的地方、故事逻辑与关系依据、阅读体验与节奏、文风契约执行、动作与空间连续性。不要为每个维度各派一位读者（本模式没有那些工具），也不要让同一位读者只答一个维度。
4. **后台派发**：省略 `run_in_background` 就是后台。**不要传 `run_in_background: false`** ——可续接模式下前台调用会退化为一次性会话，拿不到 childId，复核就送不回同一位读者。派发后记下 childId，并在回复里说明在等谁的报告。
5. **派发到回收期间暂停修改正文**：同时派出的内容必须读同一个版本。回收前改了正文，报告只能被标成旧版，那一轮等于白派。
6. **复核复用同一位读者**：修改了报告指出的实质问题，或改动影响动机、因果、视角、动作与空间状态时，用 `send_message` 发回原 childId，**只给改动范围与要问的事**，让它带着上一版的阅读继续，不必重读全文；纯措辞修改无须派发。上下文压缩后想不起 childId 时用 `list_agents` 按 `description` 找回。
7. **最终盲读另起一位全新读者**：稿件被重写、或旧报告可能让原读者带入预期时，**不要**复用原 childId，而是再派一次 `subagent_review`（全新子代理），派发消息里不给旧问题清单、修法或"哪里改过"，只给最新正文与版本——它对整篇按第一次阅读判断。这与完整版的"最终 B1 盲读"是同一条规则，同样占一个名额。
8. **派发前先跑 `story_wordcount`**，记录"正文绝对路径 + 稿件版本"；版本来自正文内容摘要，不是文件名。报告回收后再核对一次版本，版本变了就把报告标为旧版。
9. **位置用"场景编号（如有）+ 原文短引 + 行号"**；结构改动后重新定位原句，原句已改写时记录处理结果，不硬套旧段落号。
10. **名额**：一次会话新建的子代理不超过 2 位。名额主要留给这位审读员（首轮一位；之后要么 `send_message` 复用复核、要么另起一位盲读，按需取一）。通用 `subagent` 只做**不是独立审读**的活（查资料、核对某条设定）——不要拿它顶替审读员：它没有信息边界，也没有报告格式。额度不足时如实标明待审，**不虚报审读**，也不把"主代理自查"写成"独立审读"。
11. **只要评价时**，报告返回后交付意见，不自动改稿。

验收与汇总：

- 只报告影响理解或违反明确要求的问题，每条给原文锚点与影响；不把个人口味、固定的对话比例或整齐评分当成结论。
- 允许合理推断、悬念、留白与超纲的暧昧；"没有明说"不是充分的缺口证据，"没有新信息"不是删改理由。
- 作者说"我没看懂"时先定位原因：可能是信息顺序、必要依据、句子表达，也可能是有意留白。关系推进或核心转折的问题要回到正文证据，不预设必须补一拍。
- 报告缺失或复核没做时，交付里标"待审"，不声称已完成独立审读。

## 6. 交付

在当前任务中保留正文版本、审读员的 childId 与报告、必要的复核结果。正文到达约定停止位置就停止扩写，然后完成该范围的审读与修订。

交付用简短说明列出：稿件路径、实测字数、审读状态；有未解决项如实指出。只要评价或方案就交付相应成果，不顺手写正文。作者明确要求跳过某一步时按其要求调整，并说明实际检查边界。
