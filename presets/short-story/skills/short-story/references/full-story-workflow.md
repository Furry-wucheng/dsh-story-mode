# 完整故事与整体改稿流程

仅当交付物是完整故事、完整篇章或整体改稿时读取。本文件不是独立技能；操作为新写或续写本身不构成加载理由。先遵守 short-story 入口中已确定的交付范围、提问条件与文件权限。

## 约束与篇幅

沿用作者已给的字数、视角、风格与结构。只有缺失选择会实质影响交付、且无法从上下文或授权合理决定时，才用 ask_user_question 一次问完必要问题。结局倾向可以询问，但不是每篇必填；作者授权自拟或直接写时，合理决定并成稿。作者要求先看方案时再单独确认方案。

以下是选题参考，不是必须落入的范围：

| 档位 / tool tier | 字数参考 |
|---|---|
| 微型 / flash | 3000-5000 |
| 标准短篇 / short | 5000–10000 |
| 中短篇 / novelette | 10000–20000 |
| 系列每篇 / series | 3,000–10,000 |

作者给了具体字数，就直接采用，包括这些范围之外的要求。工具的 tier 只比较参考范围；具体目标以作者要求和大纲配额为准。

这些档位仅用于完整作品的篇幅参考，不作为片段的最低字数，也不因没有选择档位就阻止写作。

## 资产按需建立

新写完整故事且需要保存规划时，通常使用：

- brief.md：目标形态、作者要求、字数目标、视角、调性和禁忌等有效约束。
- outline.md：场景编号、主要内容、节奏与目标字数；涉及事件推进时再记人物目标、阻碍、处境变化与必要信息，日常或停留段不强填转折。
- draft.md：正文。

已有短稿或局部任务不强制补建前两个文件。单篇不强制建 bible.md。
跨篇设定复杂时再维护 bible.md；时间关系复杂时用 timeline.md；专名较多时用 glossary.md。多篇可在 draft/ 下一篇一个文件，共享设定；一篇写得长也不因此拆成多篇。

人物卡推荐：

~~~markdown
## 林远（别名：阿远）
- 身份：夜班司机
- 动机：找到失联的妹妹
- 关系：林青的哥哥
~~~

人物声音需要持续核对时，可在现有卡片补充说话习惯及其随关系、场合的变化，例如“对乘客客气简短，和妹妹聊天会随口絮叨；着急时才连着追问”。以作者设定和已有台词为准，不为每个人强造口头禅；这些是可选参考，不新增工具必填字段。

story_bible 只校验字段有无文字、字面提及和清单。它不判断动机成立，不识别全部新人物，也不证明专名拼写一致。共享设定的语义核对交给审读员。

## 规划与成稿

整体改稿先读获准现稿，根据实际问题决定改动；不为套流程重建大纲或共享设定。

推进事件的场景考虑：谁要什么、什么阻挡、结果怎样改变处境。日常、相处或事件后停留的场景可以写人物正在经历什么，处境和关系可以没有变化，不为填满大纲强加冲突、伏笔或领悟。
通看场景序列，按作品需要安排哪些地方快些带过、哪些让读者停留；避免所有场景都急于交付新信息。安静时刻也可以没有悬念，不必每次都写成下一次冲突的铺垫。结构和转折比例只是参考，不能把所有故事套成固定的 10% / 25% / 50% / 75% 节点，也不规定快慢交替的固定比例。

发生变化时检查：变化的触发能否在正文中感知？读者此刻理解行动所必需的信息准备在哪给？
允许悬念、延后揭示和可推断的信息，不要求背景第一次出现就讲完。缺的是理解当前行动的条件时才补。

作者要求先看方案时，给简洁方案并等待确认；已授权成稿时直接执行。若拟议方案会超出授权范围，只询问这项范围变化，不重复确认整个任务。

### 成稿

按场景成稿，必要时回读核对事实和接缝。每场结束检查时间、人物状态与前后内容能否接上；不要求场末必有决定、转折或悬念，也不为了遵守“不回读”而放任矛盾。
用工具核对已写字数和目标，不机械凑字。作者风格要求优先于 writing-style-contract 的默认风格。

## 审读与修改

派发前按 short-story 入口的“派发前先读取模板文件”规则完整读取[审读面板](review-panel.md)。本文件和 review-panel.md 同在 references/ 下；只在实际需要审读时加载面板。

完整新稿或整体重写通常采用以下顺序：

1. **初次冷读 B1**：新读者只读正文，独立报告理解障碍、阅读期待与注意力变化。意见是证据，不是必须照单全改的命令。
2. **主代理改稿**：先处理因果、人物行动与信息顺序，再处理句子。允许增删，保留有效的留白和必要交代，不设删除百分比。
3. **复核**：用 `send_message` 把改稿发回**同一位**读者，只给改动清单和它自己的旧条目（模板见审读面板）。它保留着上一版的阅读和自己的报告，不必重读全文。
4. **专项审读**：只在有具体疑问时派 B2 故事逻辑、B3 阅读体验或 B4 文风（可并行，在同一条消息里一起启动）。疑问解决了就停，不凑齐四路；局部任务不启动面板。
5. **按意见修订**：区分事实矛盾、理解障碍和口味建议，追踪每条问题的处理状态。
6. **最终盲读**：完成整体修订后，由**另一位全新读者**只读最新正文，独立报告，不给旧问题或修法。主代理在收到报告后对照旧问题。最终盲读后若再实质修改正文，相关验收需要重做。

审读员是**持久子代理**，不是一次性调用：后台派发一次（省略 `run_in_background` 就是后台），从返回的 `started subagent <childId>` 里拿到它的地址，记在当前任务中（`description` 写成角色+版本，`list_agents` 靠它认人）；此后的复核一律用 `send_message` 找同一位。**不要传 `run_in_background: false`**——在可复用模式下前台调用会退化成一次性会话，后续消息送不到，复用与缓存全部落空；要报告就等结算通知。派发后在回复里写一句在等谁的报告（这一轮会先结束，读者读完自动回来），不要一边等一边改正文。默认规模是“初次冷读 + 最终盲读”两位读者，专项审读按需添加。

报告必须对应被读稿件的版本。改稿前记录旧报告中的原句锚点，改稿后重新定位；不能拿初稿的第 N 段和新版的第 N 段直接交叉判断。完整派发模板和例外处理见[审读面板](review-panel.md)。

专项报告可以指出纯工具查不到的问题。story_lint 只给引号外的字面线索，不判第一人称、视角滑移、情绪冗余或“AI 文风”。这些都要由审读员给出上下文证据。

没有可用的独立审读工具、或作者明确不要面板时，完成授权范围内的写作和自查，说明未进行独立冷读；不能声称已通过读者验收。

## 连载审读

默认读者已经读过前面的篇目。审读当前一篇时，B1 可以按顺序读相关的**已发布前文正文**，但仍不能看大纲、设定和作者摘要。派发明确标注“连续阅读”，不要把前文已建立的信息当成本篇必须重复交代的缺口。

作者要求每篇独立可读时，才使用“独立阅读”模式，只给本篇。前文过多无法在本轮读完时，限定阅读范围，报告检查边界，不声称已验证全部跨篇一致性。

B2 按需读前文、已有 bible / timeline / glossary。没有这些文件就省略对应输入，不为审读凭空造文件。多篇逐篇计数和审读，不拼出临时总稿。

## 交付

正文保存到指定文件，说明修改范围和测得的字数。整体稿件注明独立审读是否完成、对应版本及尚未解决的问题；跳过的步骤如实说明。只汇报重要取舍，不复述整个剧情或机械统计。
