# 短篇小说写作流程

## 0. 先识别这次要做什么

以作者当前请求为准，先读指定稿件和必要上下文。已经说清的要求不要重复询问，也不要仅因缺少模板文件就阻塞工作。

| 请求 | 处理方式 |
|---|---|
| 新写完整故事 | 明确必要约束，给出简洁方案，再成稿与审读 |
| 续写已有故事或连载 | 读相关前文和已有约束，沿用确认过的设定；只确认实质性的新选择 |
| 整体改稿、重构 | 先读稿，按问题决定改稿范围；保留仍然有效的结构与作者意图 |
| 改一句、润色一段、调整某处对话 | 走局部流程，不补建接稿单、大纲或整套审读面板 |
| 只要评价、检查或建议 | 只给审读意见，不改正文，不把评价任务升级为创作任务 |

局部流程：读指定片段及必要的前后文 → 按作者要求修改 → 检查接缝、人物口吻和信息是否改变 → 简短交付。影响跨场因果、结局或共享设定时，先说明范围扩大；必要时升级为整体改稿。用户明确限制范围时遵守限制。

### 开工前先问清楚

**新写一篇时，动笔前必须先把真正影响成稿的选择问清。** 这条优先于“不重复询问”——那句话只排除作者已经给过的要求，不是不问的借口。

- 用 `ask_user_question` **一次问完**，不要一问一答地拖；每题给可选项，作者也可以自己填。
- 问的是作者还没说的那些：篇幅/字数档位、视角与时态、调性与禁忌、结局倾向（或这篇写给谁看）。已经说过的不要再问。
- 作者说“你决定”“随便”“直接写”，就跳过提问，按你的默认走，并在方案里说明你取的是什么默认值。
- 问完给一次**简洁方案**（场景序列、主要内容与节奏安排），等作者确认再成稿。作者要求直接写、或只做授权范围内的改稿时，不重复停下来等批准。
- 续写只确认实质性的新选择；局部润色和“只要评价”不提问，直接做。

**如果你是被委派的审读员：只执行派发任务。** 不进入接稿、写稿或再派审读的流程，不加载派发表禁止的材料，不调用写入工具，不再委派子代理。写作契约只供获准的文风审读员读取。

## 1. 目标形态与篇幅

独立一篇与系列连载的区别是有没有跨篇共享的设定和阅读顺序，不是目录形状或字数。能从请求和现有稿件确定时直接沿用。**篇幅档位由作者选，不要替他决定**：作者没给字数时，这属于开工前那一问，不要自己挑一个档位就动笔。

以下是选题参考，不是必须落入的范围：

| 档位 / tool tier | 字数参考 |
|---|---|
| 微型 / flash | 3000-5000 |
| 标准短篇 / short | 5000–10000 |
| 中短篇 / novelette | 10000–20000 |
| 系列每篇 / series | 3,000–10,000 |

作者给了具体字数，就直接采用，包括这些范围之外的要求。工具的 tier 只比较参考范围；具体目标以作者要求和大纲配额为准。

字数口径：中日韩字符逐字，连续的拉丁字母/数字串算一词，标点不计。工具排除 Markdown 标题和开头的元数据块。交付字数用 story_wordcount 实测，不估算。

场景目标按叙事需要分配，不要求均分。调用 story_wordcount 时将已确认的每场目标按顺序传入 sceneTargets，例如 "1000,3000"。无目标则省略，工具只报告分布。逐场写作时可传完整目标列表，未写出的后续场景会单列；最后一场尚未写完时，不把低于目标当成写作错误。

引号内文字比例仅近似反映对话量，包含引用，也漏掉无引号台词。它不是节奏评分，不设“低于 20% 偏闷 / 高于 70% 偏飘”的质量门槛。

## 2. 资产按需建立

沿用作者已有路径与文件名，不重命名或移动既有文件。新增必要文件前简短说明用途；作者没有要的说明书、索引、总结副本不要创建。

新写完整故事且需要保存规划时，通常使用：
- brief.md：目标形态、作者要求、字数目标、视角、调性和禁忌等有效约束。
- outline.md：场景编号、主要内容、节奏与目标字数；涉及事件推进时再记人物目标、阻碍、处境变化与必要信息，日常或停留段不强填转折。
- draft.md：正文。

已有短稿或局部任务不强制补建前两个文件。单篇不强制建 bible.md。
跨篇设定复杂时再维护 bible.md；时间关系复杂时用 timeline.md；专名较多时用 glossary.md。多篇可在 draft/ 下一篇一个文件，共享设定；一篇写得长也不因此拆成多篇。

人物卡推荐：
~~~markdown
## 林远（别名：阿远）
- 身份：夜班司机
- 动机：找到失联的妹妹
- 关系：林青的哥哥
~~~

人物声音需要持续核对时，可在现有卡片补充说话习惯及其随关系、场合的变化，例如“对乘客客气简短，和妹妹聊天会随口絮叨；着急时才连着追问”。以作者设定和已有台词为准，不为每个人强造口头禅；这些是可选参考，不新增工具必填字段。

story_bible 只校验字段有无文字、字面提及和清单。它不判断动机成立，不识别全部新人物，也不证明专名拼写一致。共享设定的语义核对交给审读员。

## 3. 新写或整体改稿

### 明确约束与方案

新故事先按「开工前先问清楚」把作者还没说的实质选择问出来，**一次问完**；作者已经提供的要求直接写入方案，不再逐项提问。未明确但可合理决定的细节，由你提出默认处理，并在方案里标明哪些是你定的默认值。

推进事件的场景考虑：谁要什么、什么阻挡、结果怎样改变处境。日常、相处或事件后停留的场景可以写人物正在经历什么，处境和关系可以没有变化，不为填满大纲强加冲突、伏笔或领悟。
通看场景序列，按作品需要安排哪些地方快些带过、哪些让读者停留；避免所有场景都急于交付新信息。安静时刻也可以没有悬念，不必每次都写成下一次冲突的铺垫。结构和转折比例只是参考，不能把所有故事套成固定的 10% / 25% / 50% / 75% 节点，也不规定快慢交替的固定比例。

发生变化时检查：变化的触发能否在正文中感知？读者此刻理解行动所必需的信息准备在哪给？
允许悬念、延后揭示和可推断的信息，不要求背景第一次出现就讲完。缺的是理解当前行动的条件时才补。

对新故事或显著改变现有结构的方案，给作者一次简洁确认；已有明确方案、作者要求直接写、或只做授权范围内改稿时，继续执行，不重复停下来等批准。

### 成稿

按场景成稿，必要时回读核对事实和接缝。每场结束检查时间、人物状态与前后内容能否接上；不要求场末必有决定、转折或悬念，也不为了遵守“不回读”而放任矛盾。
用工具核对已写字数和目标，不机械凑字。作者风格要求优先于 writing-style-contract 的默认风格。

### 审读与修改

**派发前先读取模板文件。** 主代理进入初次冷读、专项审读或最终盲读时，先用文件读取工具完整读取[审读面板](references/review-panel.md)，再选用其中的模板。加载本技能不等于已经加载参考文件；不要凭本节摘要或记忆编写派发要求。

路径以当前加载的本 SKILL.md 所在目录为基准：该目录下的 references/review-panel.md。先确认本技能的实际来源目录，再拼成绝对路径读取；不要相对故事目录或工作目录寻找，也不要复制进故事目录。文件内容若被截断，继续读完。已完整读取且仍在当前上下文中时可以复用；压缩后只剩摘要时重新读取。

本文件是 short-story 技能的参考资料，不是名为 review-panel 或 review-plan 的独立技能。若读取失败，报告实际路径与错误，排查安装或定位问题，不把未读取模板的派发声称为按面板流程执行。

完整新稿或整体重写通常采用以下顺序：

1. **初次冷读 B1**：新读者只读正文，独立报告理解障碍、阅读期待与注意力变化。意见是证据，不是必须照单全改的命令。
2. **主代理改稿**：先处理因果、人物行动与信息顺序，再处理句子。允许增删，保留有效的留白和必要交代，不设删除百分比。
3. **复核**：用 `send_message` 把改稿发回**同一位**读者，只给改动清单和它自己的旧条目（模板见审读面板）。它保留着上一版的阅读和自己的报告，不必重读全文。
4. **专项审读**：只在有具体疑问时派 B2 故事逻辑、B3 阅读体验或 B4 文风（可并行，在同一条消息里一起启动）。疑问解决了就停，不凑齐四路；局部任务不启动面板。
5. **按意见修订**：区分事实矛盾、理解障碍和口味建议，追踪每条问题的处理状态。
6. **最终盲读**：完成整体修订后，由**另一位全新读者**只读最新正文，独立报告，不给旧问题或修法。主代理在收到报告后对照旧问题。最终盲读后若再实质修改正文，相关验收需要重做。

审读员是**持久子代理**，不是一次性调用：后台派发一次（省略 `run_in_background` 就是后台），从返回的 `started subagent <childId>` 里拿到它的地址，记在当前任务中（`description` 写成角色+版本，`list_agents` 靠它认人）；此后的复核一律用 `send_message` 找同一位。**不要传 `run_in_background: false`**——在可复用模式下前台调用会退化成一次性会话，后续消息送不到，复用与缓存全部落空；要报告就等结算通知。派发后在回复里写一句在等谁的报告（这一轮会先结束，读者读完自动回来），不要一边等一边改正文。默认规模是“初次冷读 + 最终盲读”两位读者，专项审读按需添加。

报告必须对应被读稿件的版本。改稿前记录旧报告中的原句锚点，改稿后重新定位；不能拿初稿的第 N 段和新版的第 N 段直接交叉判断。完整派发模板和例外处理见 references/review-panel.md。

专项报告可以指出纯工具查不到的问题。story_lint 只给引号外的字面线索，不判第一人称、视角滑移、情绪冗余或“AI 文风”。这些都要由审读员给出上下文证据。

没有可用的独立审读工具、或作者明确不要面板时，完成授权范围内的写作和自查，说明未进行独立冷读；不能声称已通过读者验收。

## 4. 连载审读

默认读者已经读过前面的篇目。审读当前一篇时，B1 可以按顺序读相关的**已发布前文正文**，但仍不能看大纲、设定和作者摘要。派发明确标注“连续阅读”，不要把前文已建立的信息当成本篇必须重复交代的缺口。

作者要求每篇独立可读时，才使用“独立阅读”模式，只给本篇。前文过多无法在本轮读完时，限定阅读范围，报告检查边界，不声称已验证全部跨篇一致性。

B2 按需读前文、已有 bible / timeline / glossary。没有这些文件就省略对应输入，不为审读凭空造文件。多篇逐篇计数和审读，不拼出临时总稿。

## 5. 交付

正文保存在作者指定文件里；说明修改范围和测得的字数。新稿可指出主要取舍，改稿可指出解决了哪些问题。只汇报仍然重要的不确定项和有争议的未采纳意见，不复述整个剧情，也不重复机械统计。

局部润色通常一两句话即可。整体稿件额外注明独立审读是否完成、对应哪个版本、复用了哪些读者、跳过了哪一步，以及尚未解决的问题。稿件版本可用 story_wordcount / story_lint 报告里的内容摘要；文件变化会产生新版本。

## 工具使用边界

| 工具 | 适合做什么 |
|---|---|
| story_wordcount | 实测字数、分场、目标偏离、段落长度、引号内比例、重复双字组合 |
| story_lint | 定位字面用词线索；有命中不等于违规，无命中不等于合格 |
| story_bible | 人物卡字段非空校验、已知姓名和别名字面提及、清单提取 |
| grep / glob | 查找事实出处、前文和专名；不靠模型记忆保证一致 |
| subagent | 后台派发可复用的审读员；省略 `run_in_background`，不要传 `false` |
| send_message | 把改稿后的复核交给同一位审读员；它保留上一版的阅读和自己的报告 |
| list_agents | 找回审读员的 childId（按 `description` 里的角色与版本） |
| ask_user_question | 开工前一次问完实质选择；确认方案时也用 |
| 常规文件工具 | 所有正文和设定修改；审读员只读 |

不要用统计数字证明“好看”，也不要把读者的主观意见伪装成程序判定。
